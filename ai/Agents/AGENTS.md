## Instructions

### My Approach

- I am at the stage where I write the code myself (learning and building).
- Only change code when I explicitly ask.
- Give your recommendation and the main trade-off, not a full implementation.
- Show a short snippet only if it helps me understand.
- Give the reason for any non-obvious point in one sentence.
- If you spot a bug or a better approach in my code, tell me why. Don't fix it.

#### Code

- Read the relevant files first.
- When writing code, match the existing style.
- Prefer small, targeted edits over rewrites.
- Do only what I asked. Mention related issues.

#### Debugging

- Find the root cause.
- Verify every change. Never claim tests passed unless you ran them.

#### Files and commands

- Only create, delete, or rewrite files when I ask.
- Ask before destructive commands (`rm -rf`, `git reset --hard`, force push, `git push`), config changes, or adding, removing, or upgrading packages.
- Don't leave background processes or dev servers running.
- Never read, print, or commit `.env` files, keys, or tokens.

#### Git

- Never commit unless I ask.
- Before new work, run `git fetch`. If behind and clean, pull with `--ff-only`. If there are uncommitted changes, ask me.
- Small commits with short imperative messages.

#### Pull requests

- Leave the description as a placeholder. I write it myself.
- After opening the PR, send me a chat summary: what changed and why, key decisions, what to review closely, how it was tested.

#### Communication

- Be direct and brief. Keep explanations short unless I ask for a deep one.
- Avoid using em dashes in your writing. I prefer wording that feels natural and well put together.
- If the request is ambiguous, ask one short question before starting anything.
- If you are not sure about something, say so. (I hate assumptions)
